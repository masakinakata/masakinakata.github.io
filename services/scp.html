サービスコントロールポリシー（SCP）

AWS Organizations の機能。組織内のアカウントで「使ってよい操作の上限」を決めるポリシー。メンバーアカウントの管理者や root ユーザーでも越えられない予防的なガードレールになる。

構成図

仕組みと主な機能

基本ルール

  • Root、OU、アカウントに付与でき、下位へ継承される。どこか 1 つでも拒否されれば拒否。
  • SCP は権限を付与しない。許可するには別途 IAM ポリシーが必要。
  • メンバーアカウントの root ユーザーにも効く。一方で管理アカウントには効かない。サービスにリンクされたロールにも効かない。

拒否リスト方式と許可リスト方式

  • 拒否リスト方式（推奨）：デフォルトの FullAWSAccess を残し、禁止したい操作だけを Deny で書く。
  • 許可リスト方式：FullAWSAccess を外し、使ってよいサービスだけを Allow で列挙する。厳しいが保守が大変。

よく使う SCP の例

  • 許可リージョン以外の利用を禁止（aws:RequestedRegion 条件 + グローバルサービスを NotAction で除外）
  • CloudTrail の停止、GuardDuty / Config の無効化を禁止
  • 組織からの脱退（organizations:LeaveOrganization）を禁止
  • 特定のタグがないリソースの作成を禁止

RCP（リソースコントロールポリシー）

SCP が「組織内のプリンシパルが何をできるか」を制限するのに対し、RCP は「組織内のリソースに対して誰が何をできるか」を制限する。たとえば組織外からの S3 アクセスを一律に拒否するなど、データ境界の構築に使う。

統制の種類

種類代表的な仕組み効果
予防的SCP、RCP、IAM ポリシー、アクセス許可の境界操作そのものを止める
発見的AWS Config ルール、Security Hub、GuardDuty違反を検知して通知する
是正的Config の自動修復、EventBridge + Lambda違反を自動で元に戻す

試験で狙われるポイント

  • 「アカウント管理者でも回避できない」「組織全体」「予防」→ SCP。
  • SCP は管理アカウントには効かない。そのため管理アカウントではワークロードを動かさない。
  • IAM ポリシーやアクセス許可の境界は、そのアカウントの管理者が外せるうえ root ユーザーに効かないので、「回避できない」要件を満たさない。
  • AWS Control Tower の「コントロール」は、SCP（予防）と Config ルール（発見）をまとめて展開する仕組み。
