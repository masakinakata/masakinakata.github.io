移行

AWS DMS（Database Migration Service）とスキーマ変換

データベースを AWS へ移行するサービス。ソースを動かしたままデータを複製し続けられるので、停止時間を短く抑えられる。異なる DB エンジン間の移行では、先にスキーマ変換（AWS SCT / DMS Schema Conversion）を行う。

構成図

仕組みと主な機能

DMS の構成要素

  • レプリケーションインスタンス（または DMS Serverless）：移行処理を実行する。
  • エンドポイント：ソースとターゲットの接続情報。ターゲットには RDS / Aurora のほか、S3、DynamoDB、Kinesis、Redshift なども指定できる。
  • タスク：全ロードのみ / 全ロード + CDC / CDC のみ から選ぶ。テーブルの選択や名前の変換もここで設定する。

CDC（変更データキャプチャ）

  • ソース DB のトランザクションログを読んで、変更をターゲットに反映し続ける。
  • ソースごとに準備が必要（例：Oracle はサプリメンタルロギング、MySQL は binlog を ROW 形式に）。
  • データ検証機能で、ソースとターゲットの行を比較できる。

DMS がやらないこと

  • DMS が作るのはテーブルと主キー程度。セカンダリインデックス、外部キー、ストアドプロシージャ、トリガー、ユーザーなどは移行しない。
  • 異種エンジン間では、これらを AWS SCT または DMS Schema Conversion で変換する。自動変換できない部分は評価レポートで確認して手で直す。

移行パターンの整理

パターン例主な手段
同種移行MySQL → RDS for MySQL / Aurora MySQLネイティブツール（ダンプ、レプリケーション）、DMS
異種移行Oracle → Aurora PostgreSQLSCT / DMS Schema Conversion + DMS
DWH 移行Oracle / Teradata → RedshiftSCT（データ抽出エージェント）+ DMS

試験で狙われるポイント

  • 「停止時間を最小化」→ DMS の 全ロード + CDC。
  • 「エンジンを変える」「ライセンス費用を削減」→ スキーマ変換（SCT / DMS Schema Conversion）が必要。
  • データ量と回線帯域から転送時間を見積もる問題が出る（5 TB ÷ 1 Gbps ≒ 約 11 時間）。全ロードだけで停止時間内に終わらないなら CDC を使う。
