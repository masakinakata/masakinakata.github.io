移行

AWS Application Migration Service（MGN）

物理サーバー、VMware、Hyper-V、他クラウドのサーバーを、そのまま AWS へ移す（リホスト）ためのサービス。ディスクを継続的に複製しておき、テスト起動で確認してから短い停止時間で切り替える。

構成図

仕組みと主な機能

移行の流れ

  1. ソースサーバーに AWS Replication Agent をインストールする（vCenter 環境ではエージェントレスの複製も可能）。
  2. 初回の全体同期のあと、変更が継続的にステージングエリアへ複製される。
  3. テストインスタンスを起動して動作確認する。この間もソースは動いたまま。
  4. 本番切り替え（カットオーバー）：アプリを止め、最終同期の後に本番インスタンスを起動して DNS などを切り替える。
  5. 問題なければソースとの複製を切り離し、アーカイブする。

主な機能

  • 起動テンプレートでインスタンスタイプやサブネット、セキュリティグループを事前に設定できる。
  • 起動後のアクション（SSM ドキュメント）で、移行後のエージェント導入や設定変更を自動化できる。
  • 複数サーバーをアプリケーション / ウェーブ単位でまとめて操作できる。
  • サービス自体はソースサーバーごとに一定期間無料。ステージングエリアの EC2 や EBS の料金はかかる。

移行戦略「7 つの R」

戦略概要代表的なサービス
Rehost（リホスト）そのまま移すAWS MGN
Replatform（リプラットフォーム）一部をマネージドサービスに置き換えRDS、Elastic Beanstalk
Repurchase（再購入）SaaS に乗り換え—
Refactor（リファクタリング）クラウドネイティブに作り直すLambda、ECS、DynamoDB
Relocate（リロケート）ハイパーバイザーごと移すVMware Cloud on AWS など
Retain / Retire保持 / 廃止—

試験で狙われるポイント

  • 「リホスト」「大量のサーバー」「停止時間を最小化」「テスト起動」→ AWS MGN。
  • VM Import/Export は少数台の単発移行向けで、変換中はサーバーを止める必要がある。
  • 「何を移すか」でサービスを切り分ける：サーバー → MGN、DB → DMS、ファイル → DataSync。
