Amazon SQS（Simple Queue Service）

フルマネージドなメッセージキュー。送り手と受け手の間にキューを挟むことで処理を非同期にし、アクセスの急増を吸収したり、障害の影響を切り離したりできる。

仕組みと主な機能

標準キューと FIFO キュー

項目標準キューFIFO キュー
順序ベストエフォートメッセージグループ ID ごとに厳密に保証
配信少なくとも 1 回（重複の可能性あり）重複排除により 1 回だけ処理
スループットほぼ無制限上限あり（バッチ処理や高スループットモードで拡張）

重要な設定

  • 可視性タイムアウト：受信したメッセージを、ほかのワーカーから見えなくする時間（デフォルト 30 秒、最大 12 時間）。処理時間より長くしないと二重処理になる。
  • メッセージ保持期間：1 分〜14 日（デフォルト 4 日）。
  • ロングポーリング：受信待ちを最大 20 秒にして、空振りの API 呼び出しとコストを減らす。
  • デッドレターキュー（DLQ）：一定回数（maxReceiveCount）処理に失敗したメッセージを隔離する。調査後に元のキューへ戻す（リドライブ）こともできる。
  • 遅延キュー / メッセージタイマー：配信を最大 15 分遅らせる。
  • 大きなデータは S3 に置いてキューには参照だけを入れる（Extended Client Library）。

メッセージング系サービスの使い分け

サービスモデル向いている用途
SQSキュー（プル型）。処理したら削除ワーカーへの作業分配、スパイク吸収
SNSPub/Sub（プッシュ型）1 つのイベントを多数の宛先へ同時配信（SQS へのファンアウトなど）
EventBridgeイベントバス + ルールイベントの中身に応じたルーティング、SaaS 連携、スケジュール
Kinesis Data Streamsストリーム（保持・リプレイ可）大量データのリアルタイム処理、複数コンシューマー

試験で狙われるポイント

  • 「リクエストを失わない」「スパイクを吸収」「疎結合」→ SQS。
  • SQS に連動したスケーリングは「インスタンスあたりのバックログ」をターゲット追跡するのが AWS 推奨。
  • 「同じメッセージが二重に処理される」→ 可視性タイムアウトが短すぎる、または冪等性がない。
  • 「順序が必要」→ FIFO キュー（メッセージグループ ID）。ただしスループットの上限に注意。
